Case studies

Four problems, in full

The GST that quietly became zero

NestJS, Redis, production debugging

Problem
A projected read was writing a partial app-configuration document under the shared cache key. Every later reader got a document with no tax field, so GST silently dropped to zero on customer fare quotes. Booking quotes hit that key constantly, so the cache stayed poisoned almost permanently.
What I did
Traced a wrong fare back through the quote path into the cache layer, and stopped projected reads from ever populating the shared key.
Result
Fares charge the correct tax again. Nothing had ever thrown an error - the only symptom was revenue quietly going missing.

A performance pass where every number was measured

NestJS, Puppeteer, MongoDB

Problem
The admin dashboard and both apps felt slow, but nothing was instrumented and the usual suspects were innocent - indexes, the Redis session cache and the driver location pings all turned out to be sound.
What I did
Audited the whole request path. Replaced a Chrome launch per PDF with one shared instance capped at four concurrent renders, cached exchange rates for twelve hours with in-flight de-duplication and last-known-good fallbacks, put deadlines on all 26 outbound HTTP calls, enabled gzip, and configured the Mongo connection pool and socket timeout.
Result
PDF rendering fell from 2.94s to 614ms, the admin bookings payload shrank 92.6%, and the live currency call disappeared from every fare quote. Every change measured before and after.

An audit trail the business can actually read

NestJS interceptors, data privacy

Problem
The first version of the staff audit log stored raw request bodies - including login credentials in plaintext - and recorded driver and customer app traffic, where location pings alone produced around 27,000 rows a day and buried the staff activity the log existed for.
What I did
Redacted the bodies, migrated the stored credentials out, scoped recording to staff only, and rebuilt the entry itself: which record changed, which fields changed, and their before and after values, with CSV export. Made logging best-effort, so a failure while recording can never roll back the action it is recording.
Result
A log an operations manager can read - "Driver / via Admin", and the exact fields that changed - instead of URL fragments and IP addresses.

Knowing when to roll back

RBAC, release judgement

Problem
A granular module.action permission system replaced whole-module grants across the API and the admin panel. Within hours it locked fleet owners out of routes their deployed portal depends on, then cost staff accounts endpoints they had been using daily.
What I did
Reverted the permission model to what was already deployed rather than keep patching live access, then re-shipped only the part with clear value - grant and revoke - on top of the working system. A global validation pipe enabled the same week had switched on 411 validators that had never once run and was failing every driver edit; that came out the same morning, with the safe re-enable sequence written into the code.
Result
Access restored the same day, the useful half of the change kept, and the rollback documented so the upgrade can be retried deliberately instead of abandoned.
