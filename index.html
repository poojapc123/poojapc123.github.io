    2.94 s → 614 ms

    One shared headless browser instead of one launched per document. 4.8x faster after the first render.

  • Admin bookings payload

    10,503 B → 779 B

    gzip response compression, loaded defensively so a missing module warns instead of stopping the API booting.

  • Live currency calls per fare quote

    1 → 0

    12-hour cache, in-flight de-duplication, last-known-good rates so quotes survive provider outages.

  • Outbound calls with a deadline

    0 of 26 → 26 of 26

    15s globally, 6s for Google Maps on booking and dispatch paths. Previously every call could hang indefinitely.

  • Deleted drivers blocking Aadhaar re-registration

    198 → 0

    Duplicate checks and two unique indexes counted soft-deleted accounts. Archived their numbers on delete and excluded them from the check.

  • Live sessions on one fleet account

    43 → 1

    Fleet logins never expired or replaced older sessions. Purged to the newest per account and moved the app-to-portal handoff into a URL fragment that never reaches server logs.

Real production incidents, told end to end.

A performance pass where every number was measured

NestJS, Puppeteer, MongoDB

Problem
The admin dashboard and both apps felt slow, but nothing was instrumented and the usual suspects were innocent - indexes, the Redis session cache and the driver location pings all turned out to be sound.
What I did
Audited the whole request path. Replaced a Chrome launch per PDF with one shared instance capped at four concurrent renders, cached exchange rates for twelve hours with in-flight de-duplication and last-known-good fallbacks, put deadlines on all 26 outbound HTTP calls, enabled gzip, and configured the Mongo connection pool and socket timeout.
Result
PDF rendering fell from 2.94s to 614ms, the admin bookings payload shrank 92.6%, and the live currency call disappeared from every fare quote. Every change measured before and after.

The GST that quietly became zero

NestJS, Redis, production debugging

Problem
A projected read was writing a partial app-configuration document under the shared cache key. Every later reader got a document with no tax field, so GST silently dropped to zero on customer fare quotes. Booking quotes hit that key constantly, so the cache stayed poisoned almost permanently.
What I did
Traced a wrong fare back through the quote path into the cache layer, and stopped projected reads from ever populating the shared key.
Result
Fares charge the correct tax again. Nothing had ever thrown an error - the only symptom was revenue quietly going missing.

The login that undid itself

Flutter, NestJS guards, on-device debugging

Problem
Drivers entered the OTP, reached Home, and were thrown back to Sign Up a moment later - on every launch. The token was being saved correctly, which made the symptom look impossible from the client code alone.
What I did
Read the device log instead. On Home load one earnings endpoint answered 401 "no permission" from a role guard while every other call on the same token returned 200. The client treated any 401 or 403 as an expired session, navigated to login and wiped the token it had stored 300 ms earlier. Narrowed the logout to a genuine dead session - an "unauthorized" error code or a failed profile read - and left resource denials alone. Then found the production API was a stale build whose driver routes sat under an admin wildcard, and redeployed it with a backup and a rollback path.
Result
Login sticks. Two bugs behind one symptom: a client that over-reacted and a server that had never been deployed.

Notifications that never popped

Firebase Cloud Messaging, Android channels

Problem
Every push landed in the in-app inbox, so the backend looked fine, yet nothing ever showed on the phone. Drivers missed cancellations and general alerts.
What I did
The backend sent a channel id with a typo, so Android fell back to a default channel at normal importance - tray only, no banner. Fixed the id and priority on the server, created the high-importance channel natively on app start so it exists before the first push, and sequenced the two Android permission prompts so the second was no longer dropped. Ride requests and cancellations then moved to data-only high-priority messages handled by the app's own background service, with a native player for the cancellation voice.
Result
Banners, ringtone and the cancel voice work in the foreground, in the background and after the app is swiped away - verified on a real device rather than from the inbox rows.

A second API on a live host, with no DNS to spare

Apache, PM2, NestJS, Flutter

Problem
A new customer app arrived with its own NestJS service on another port, sharing a JWT secret and a database with the existing booking API. It had to go live on the existing server with no wildcard DNS and no disruption to the driver app.
What I did
Audited both stacks and wrote a working/broken report before touching code: which routes could move to the new service (auth, profile, places, share-tracking) and which had to stay on the shared API (quotes, bookings, dispatch, sockets, wallet, payments). Exposed the new service as a PM2 app behind path-based Apache proxy rules on the existing API host, gave the Flutter app a per-environment customer-API base URL, and staged install and vhost scripts with backups, config tests and rollback for the owner to run.
Result
Verified end to end against production from an emulator - OTP login on the new service, the token accepted by the legacy API, a booking created and dispatched, push delivered, the public share-tracking page served, uploads landing in object storage. The driver app was never touched.

An audit trail the business can actually read

NestJS interceptors, data privacy

Problem
The first version of the staff audit log stored raw request bodies - including login credentials in plaintext - and recorded driver and customer app traffic, where location pings alone produced around 27,000 rows a day and buried the staff activity the log existed for.
What I did
Redacted the bodies, migrated the stored credentials out, scoped recording to staff only, and rebuilt the entry itself: which record changed, which fields changed, and their before and after values, with CSV export. Made logging best-effort, so a failure while recording can never roll back the action it is recording.
Result
A log an operations manager can read - "Driver / via Admin", and the exact fields that changed - instead of URL fragments and IP addresses.

Knowing when to roll back

RBAC, release judgement

Problem
A granular module.action permission system replaced whole-module grants across the API and the admin panel. Within hours it locked fleet owners out of routes their deployed portal depends on, then cost staff accounts endpoints they had been using daily.
What I did
Reverted the permission model to what was already deployed rather than keep patching live access, then re-shipped only the part with clear value - grant and revoke - on top of the working system. A global validation pipe enabled the same week had switched on 411 validators that had never once run and was failing every driver edit; that came out the same morning, with the safe re-enable sequence written into the code.
Result
Access restored the same day, the useful half of the change kept, and the rollback documented so the upgrade can be retried deliberately instead of abandoned.
